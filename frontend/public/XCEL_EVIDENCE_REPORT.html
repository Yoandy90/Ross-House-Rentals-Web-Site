Green Button Connect — OAuth Authorization Flow Failure
Technical Evidence for Replication

Vendor: Ross House Rent (client_id 9dcf7385177c67119581) · Prepared: July 15, 2026 · Contact: yoandyross@rosshouserentals.com

Summary: The vendor-initiated OAuth authorization flow fails for every customer. The /oauth/authorize endpoint itself responds correctly, but it redirects the customer's browser to wsservices.xcelenergy.com, which does not respond to any connection attempt (TCP connect timeout). The customer therefore sees a blank page and can never reach the consent screen. Reproduction takes under 2 minutes with the steps below.

STEP 1 — Customer opens the authorization URL (what the end user does)

URL opened in a normal browser (Chrome, logged in or not — result is identical):

https://myenergy.xcelenergy.com/greenbutton-connect/gbc/espi/1_1/oauth/authorize?client_id=9dcf7385177c67119581&redirect_uri=https%3A%2F%2Fwww.rosshouserentals.com%2Ftenant%2Futilities%3Fcallback%3Dgreenbutton&response_type=code&scope=FB%3D1_3_4_5_10_13_15_31_37_39&state=VkJr9IqTqRTah-R21UznzgX1ZaaABokW
Observed result: The browser redirects and then hangs, ending on a blank white page. Chrome DevTools shows the final navigation error: net::ERR_CONNECTION_TIMED_OUT at wsservices.xcelenergy.com. Tested on July 15, 2026 from multiple networks (residential ISP in Texas and a cloud datacenter) — identical behavior.

STEP 3 — wsservices.xcelenergy.com never responds (the failure point)

$ python3 -c "import socket; print(socket.gethostbyname('wsservices.xcelenergy.com'))"
192.234.135.91          # DNS resolves correctly

$ curl -sk -o /dev/null -w "connect:%{time_connect} http:%{http_code}" --max-time 40 "https://wsservices.xcelenergy.com/"

Analysis: DNS resolves to 192.234.135.91, but the host never completes a TCP connection on port 443. Since the customer's browser is redirected here for the SAML login, the flow dies with a blank page 100% of the time.
